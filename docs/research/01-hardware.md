# Technical Report: Building a Noise-Reduction Power-Shaping Tool in Rust for the Framework 16 (2025, HX 370 + RTX 5070) on Fedora

## TL;DR
- **The tool is viable, but with a split strategy: CPU power is directly controllable via `ryzenadj` (PPT limits work on Strix Point even though full PMTable readback does not), while the GPU must be shaped by *locking the maximum graphics clock* (`nvidia-smi -lgc`), because `nvidia-smi -pl` power limiting is confirmed rejected on Blackwell mobile GPUs.**
- **Fan topology is the biggest hardware unknown: the FW16 exposes two EC fan channels (`fan1_input`/`fan2_input`), but the fans sit on a shared CPU+GPU cooling assembly and the dGPU module's fan is Framework's "Graphics Module Fan"; there is no evidence of a software-invisible third fan, but the exact channel-to-physical mapping and max RPM must be measured on the machine.**
- **Coordinate with (or disable) `tuned`/`power-profiles-daemon` and `nvidia-powerd`, reapply all limits after every suspend/resume via a systemd sleep hook, and treat very-low PPT as safe (it throttles, it does not brick) — the primary safety risks are instability/hangs at extreme settings and silently losing limits after resume.**

## Key Findings

1. **Fans:** The Framework 16 exposes two software-visible fans through the `cros_ec`/`framework_laptop` hwmon. The 2025 RTX 5070 module ships with the "Graphics Module Fan," which Framework's store page describes as a *"75mm x 11.5mm Cooler Master fan that sits in the Graphics Module to provide powerful and quiet cooling for the CPU and GPU simultaneously"* — i.e., the fans cool CPU and GPU together across a shared assembly. The stock EC fan curve keeps fans off until roughly 47 °C.
2. **CPU:** `ryzenadj` v0.19.0+ can set STAPM/PPT limits on the HX 370 (Family 1Ah / Strix Point), though many PMTable fields read back `nan`. Limits are in **milliwatts**. Platform-profile events (notably resume from suspend, and PPD/tuned/GameMode profile switches) can silently override them.
3. **GPU:** `nvidia-smi -pl` is rejected on Blackwell mobile ("not supported in current scope"). The working lever is `nvidia-smi -lgc <min>,<max>` / NVML `nvmlDeviceSetGpuLockedClocks`, callable from Rust via the `nvml-wrapper` crate. Locking the max graphics clock indirectly caps sustained power and heat.
4. **Interference:** On Fedora, `tuned` (default since Fedora 41) or `power-profiles-daemon` drives the ACPI `platform_profile` and amd-pstate EPP; `nvidia-powerd` manages NVIDIA Dynamic Boost; GameMode can change CPU governor/platform profile and (if explicitly configured) GPU clocks. AMD SmartShift does **not** apply with an NVIDIA dGPU.
5. **Safety:** Low PPT is generally safe (the CPU just throttles), but limits do **not** persist across suspend/resume and must be reapplied. Reset CPU via re-applying stock values or reboot; GPU via `nvidia-smi -rgc`/`-rmc`.

## Details

### 1. Fan topology of the Framework 16 (2025 refresh)

**Physical layout.** The Framework 16 uses a shared cooling design in which the expansion-bay module carries the system fan(s). Framework's own store lists the **"Framework Laptop 16 Graphics Module Fan"** as a *"75mm x 11.5mm Cooler Master fan that sits in the Graphics Module to provide powerful and quiet cooling for the CPU and GPU simultaneously."* This is the critical architectural fact: when the discrete GPU module is installed, its fan participates in cooling **both** the CPU and the GPU across a shared heatpipe/heatsink assembly, rather than being a GPU-only fan isolated from the CPU. (For contrast, the GPU-less default Expansion Bay Module uses "dual 75mm x 8.2mm Cooler Master fans," per frame.work/laptop16 — a different fan count depending on the installed module.) Framework's 2025 launch blog ("Introducing the new Framework Laptop 16 with NVIDIA® GeForce RTX™ 5070") states they *"revamped the thermal system, switching to Honeywell phase change thermal interface material and reoptimizing the fan blade geometry and controller IC for reduced noise while supporting 100W sustained TGP."*

**Software channels.** The machine's baseline shows two channels, `fan1_input` and `fan2_input`, both reporting ~1450 RPM, exposed through the `cros_ec`/`framework_laptop` hwmon driver (Framework's EC is a fork of ChromeOS EC / CrOS EC). The community fan-control tool `fw-fanctrl` documents that it *"is compatible with all 13" and 16" models, both AMD/Intel CPUs, with or without a discrete GPU"* and drives the EC through `framework_tool`; when stopped, *"the fans will revert to their default behaviour."* This confirms both fans are addressable through the EC and that stock behavior is restored automatically when software releases control — the exact property the noise tool relies on.

**Which fan is which.** The exact `fan1`↔`fan2` to physical-fan mapping for the FW16 is **not documented in a primary Framework source** and should be treated as uncertain/version-dependent. In the general hwmon/lm-sensors world, channel numbering is not guaranteed stable across reboots or kernel updates. Because the fans share a single CPU+GPU cooling assembly, the practical distinction between a "CPU fan" and a "GPU fan" is weak on this platform — both respond to the combined thermal load. **This must be confirmed empirically on the actual machine** by forcing one channel with `ectool fanduty`/`framework_tool` and observing which RPM reading and which temperature responds.

**Is there a hidden dGPU fan?** Evidence indicates the dGPU module fan IS the software-visible EC fan (the "Graphics Module Fan" is EC-controlled and appears via the EC hwmon), not a separate software-invisible fan. There is no primary-source evidence of a third, invisible fan on the FW16 dGPU module. The `amdgpu` hwmon `fan1` (the iGPU/Radeon 890M) typically reads N/A because the 890M is an integrated GPU without its own fan. The NVIDIA dGPU does not expose a fan tach through `nvidia-smi` on this laptop (mobile GPUs generally do not). **Flag: whether the RTX 5070 module contributes one or two tach channels, and how they map to `fan1`/`fan2`, needs on-machine confirmation** — especially since the default (GPU-less) module has two fans while the GPU module's product page describes a single fan.

**Max RPM.** No authoritative published max-RPM figure for the FW16 fans was found. (I could not verify a specific dB noise figure from a major review; one Framework Community owner thread, "5400hz sound from dGPU fan on new Framework 16," documents a *"~5400hz sound that is around -54 db around 4 inches from the back of the dGPU module"* under load, but that is an anecdotal acoustic report, not a fan-RPM spec.) Max RPM must be read from the machine (e.g., `fanX_max` if exposed, or by forcing 100% duty and reading `fanX_input`).

**EC fan-curve behavior.** The stock EC curve is quiet-biased. A Framework Community post by Amar_Persaud states: *"The fan curves on the laptop has the fans not turn on until the CPU/APU temperature reaches around 47C. 40C is around where it will start to get pretty uncomfortable."* The EC firmware logic lives in the open-source `FrameworkComputer/EmbeddedController` repo (the `lotus`/`lotus-zephyr` program tree, e.g., `cpu_power.c`), which is also where CPU/GPU power sharing is implemented at the EC level. Precise threshold tables and hysteresis values are in that firmware source and are **BIOS/EC-version-dependent**; they are not published as a stable spec. The tool's premise — reduce heat so the EC spins fans down on its own stock curve — is sound precisely because the EC curve is temperature-driven with a ~47 °C spin-up point and restores automatically.

### 2. CPU power limiting on Strix Point (Ryzen AI 9 HX 370)

**Does `ryzenadj` work?** Yes, with caveats. Early builds failed (`Fam1ah: unsupported model 36 / Unsupported family: 1ah`), but FlyGoat's RyzenAdj issue #309 tracked adding Strix Point support, and the maintainer confirmed: *"I received off-issue test reports stating that at least PPT adjustment features are working, will merge test changes into master."* A HX 370 dump in that thread (v0.18.0, PM Table `5d0009`) shows **STAPM LIMIT, PPT LIMIT FAST, and PPT LIMIT SLOW parse correctly** (e.g., STAPM 85 W / FAST 100 W / SLOW 85 W), while most other rows (TDC/EDC/temperatures/STT skin temps) read `nan`. The v0.19.0 release notes add a "strix point table from ryzen_smu" and "added support for PRO variant of HX 370." **Conclusion: STAPM/fast/slow PPT setting works on the HX 370; fine-grained current/temperature/skin-temp controls and full readback do not.** This is version-dependent — use RyzenAdj ≥ v0.19.0.

**Exact semantics (units and windows):**
- `-a, --stapm-limit=<u32>` — Sustained Power Limit (STAPM), in **mW**. The RyzenAdj wiki: *"It is the 3rd level Power limit, used after fast limit and after slow limit. Gets overwritten by STTv2."* Governed by `--stapm-time` (STAPM constant time, seconds) — the longest averaging window (skin-temperature / sustained thermal).
- `-b, --fast-limit=<u32>` — "Actual Power Limit" / PPT LIMIT FAST, in **mW**. Shortest time window; the instantaneous/burst ceiling.
- `-c, --slow-limit=<u32>` — "Average Power Limit" / PPT LIMIT SLOW, in **mW**. Medium window, governed by `--slow-time` (Slow PPT constant time, seconds).
- Sanity relationship (from the RyzenAdj wiki): **Fast Limit ≥ Slow Limit ≥ STAPM Limit** ("Values above slow limit or fast limit would not make sense").
- Units are all milliwatts: `--stapm-limit=45000` = 45 W. `--tctl-temp=<u32>` is in °C.

For a noise tool, the operative knobs are `--slow-limit` and `--stapm-limit` (they govern sustained draw and therefore sustained heat), with `--fast-limit` set equal or slightly higher to permit brief bursts without sustained heat. Optionally lower `--tctl-temp` to force earlier CPU-side throttling.

**Known override issues.** RyzenAdj's own README warns: *"some settings could get overwritten by power management features of your device, and you need to regularly set your values again."* On Framework AMD specifically, the community-tracked bug "[TRACKING] PPD changes have no effect after suspend on AMD until reboot" documents that `/sys/firmware/acpi/platform_profile` writes (what PPD/tuned use) stop taking effect after suspend/resume — visible by watching `ryzenadj -i`. This means: (a) a platform-profile change (PPD/tuned/GameMode) can move the SMU limits out from under you, and (b) after resume the whole power-limit state can be stale. Reapply on a timer and on resume.

**`ryzen_smu` kernel module.** RyzenAdj prefers the `ryzen_smu` module and falls back to `/dev/mem`. Minimum supported version is 0.1.7; the active fork is `amkillam/ryzen_smu` (DKMS). Strix Point support in RyzenAdj v0.19.0 came from the ryzen_smu Strix Point table. Note one issue-thread report of `Unable to get RSMU Obj / Unable to init ryzenadj` on a recent build — so ryzen_smu compatibility is itself version-sensitive. If ryzen_smu misbehaves, the `/dev/mem` path (with `iomem=relaxed` on some kernels) is the fallback.

**UXTU / sysfs-native.** Universal x86 Tuning Utility uses `ryzenadj` as its engine, so it offers no independent Linux path. There is **no sysfs-native STAPM/PPT interface**: the machine's baseline confirms `/sys/class/powercap/intel-rapl` exposes only `energy_uj` with **no writable constraints** on this platform, so the powercap route cannot set CPU power limits here. SMU-based `ryzenadj` is the only working method.

**Reading back applied limits and actual draw.** Because the HX 370 PMTable reads mostly `nan` under RyzenAdj, reliable *readback of the applied limit* is limited — `ryzenadj -i` shows STAPM/PPT limit and value rows but not the fuller table. For **actual sustained power**, RAPL energy is the path: on Zen 5 the package energy counter is exposed through the powercap tree's `energy_uj` (microjoules; differentiate over time to get watts). Note the Family 1Ah RAPL check was initially missing in Linux 6.10 and required a one-line patch (per Phoronix's HX 370 review); it has since been upstreamed, so a modern Fedora kernel (6.11+) should report AMD package energy. The path appears under the `intel-rapl` control type (the powercap framework reuses that name for AMD too) — the machine baseline confirms `intel-rapl/.../energy_uj` exists. Alternative telemetry: the `amdgpu` hwmon exposes iGPU `PPT` in watts, and third-party `zenpower5` adds Zen 5 RAPL-based power monitoring (but requires blacklisting `k10temp` and is DKMS). **Recommendation: read `energy_uj` deltas for CPU package power; do not rely on RyzenAdj PMTable readback on this APU.**

### 3. GPU control on Blackwell mobile (RTX 5070 Laptop GPU)

**`-pl` is rejected — confirmed.** Multiple NVIDIA Developer Forum threads confirm Blackwell mobile rejects power-limit changes. On an RTX 5080 laptop (HP OMEN Max 16): *"nvidia-smi -pl 175 just says 'not supported in current scope', which I know is expected for Blackwell laptop GPUs."* Earlier RTX 50/40-series mobile threads show the same `Changing power management limit is not supported in current scope` error (and the closely related `... not supported for GPU` on other mobile parts). The machine baseline (5–100 W range reported by `-q -d POWER`, but `-pl` rejected) matches this exactly. The 100 W max aligns with Framework's stated "100W sustained TGP" for the module (corroborated by Tom's Hardware). **Root cause:** NVIDIA moved laptop TGP control behind the SBIOS / Dynamic Boost path (`nvidia-powerd`), removing direct `-pl` on mobile.

**`-lgc` (lock GPU clocks) is the working lever.** On desktop Blackwell (RTX 5080, driver 580.65.06) `sudo nvidia-smi -lgc <MHz>` is confirmed to work and clamp the graphics clock (Folding@home forum report). The Arch community explicitly recommends clock adjustment as the substitute for the blocked `-pl` on laptops. **Caveat: no primary source was found showing a user on an actual RTX 5070/5080 *Laptop* GPU demonstrating `-lgc` clamping clocks/power** — treat mobile `-lgc` success as *probable but unverified pending on-machine test*. There is no report of `-lgc` being rejected with "not supported in current scope" on mobile (that error is specific to `-pl`), and the nvidia-smi documentation lists `-lgc` as broadly supported (Kepler+) with no laptop carve-out. NVIDIA staff (Robert_Crovella) caution that on GeForce cards "it's not possible to make any sort of clock adjustments … that would violate the GPU's attempt to protect itself or stay within its power budget."

**Does locking max clock cap sustained power/heat?** Yes, indirectly. Because voltage/frequency are coupled, setting a lower maximum graphics clock lowers the GPU's operating point and thus sustained power and heat. ArchWiki documents a desktop example where lowering the boost-clock limit "reduces power consumption by 30%, temperature from 75 to 63 degrees" on an RTX 3090 Ti. **Important limitation** (indii.org / NVIDIA staff): this is a *ceiling*, not a hard power cap — "The thermal throttle still governs the hardware," and NVIDIA's clock algorithm "will take over" to protect the power budget. So `-lgc <max>` reliably lowers *sustained* clocks/heat under sustained load, which is exactly what a noise tool needs, but it cannot guarantee a fixed wattage.

**Memory clocks (`-lmc`).** `nvidia-smi --lock-memory-clocks` is **unreliable on GeForce**; on a desktop RTX 5090 (driver 580.95.05) both `-lgc` and `-lmc` were reported to fail/not lock in one thread, and memory-clock locking has historically been flaky on consumer cards (which expose few memory-clock states). **Do not rely on `-lmc` for Blackwell mobile.** Focus on `-lgc`.

**Granularity.** Graphics clocks are quantized: `nvidia-smi -q -d SUPPORTED_CLOCKS` returns a discrete list of valid values, and recent GeForce clock offsets move in **15 MHz steps** ("Clock offset moves in increments of 15MHz rounded-down"). NVML `nvmlDeviceSetGpuLockedClocks` returns `NVML_ERROR_INVALID_ARGUMENT` for an invalid min/max combination; the driver snaps to the nearest supported value. Design the tool to pick from the supported-clocks list or round to 15 MHz.

**Persistence mode.** `nvidia-smi -pm 1` is **not required to apply** a lock (you only get a warning without it) but **is needed for the lock to survive driver unload/reload** — per NVIDIA/Dell/Microway docs, "Any settings below for clocks and power get reset between program runs unless you enable persistence mode." Enable it for robustness.

**Latency.** Applying a clock lock is effectively immediate (a single NVML call); no primary latency figure was found, but it is a synchronous driver call on the order of milliseconds. Persistence mode also makes `nvidia-smi` invocations faster.

**Rust integration.** Prefer calling NVML directly over shelling out to `nvidia-smi`. The `nvml-wrapper` crate (rust-nvml/nvml-wrapper) is a safe, ergonomic wrapper that loads `libnvidia-ml.so` at runtime via `libloading`; the underlying `nvml-wrapper-sys` exposes `nvmlDeviceSetGpuLockedClocks(device, minGpuClockMHz, maxGpuClockMHz)`. This avoids parsing `nvidia-smi` text output, gives typed errors (e.g., `NotSupported`, `NoPermission`), and lets you look up devices by PCI bus ID/UUID (recommended, since NVML index is not stable across reboots). Run as root/CAP_SYS_ADMIN. Note `nvmlDeviceSetMemoryLockedClocks` historically was missing from the wrapper's bindings (issue #26) — another reason to rely on GPU (graphics) clock locking, not memory.

### 4. Interference sources on Fedora

- **tuned (default since Fedora 41 Workstation/KDE/Budgie):** This change was approved by the Fedora Engineering Steering Committee (FESCo) for Fedora 41; the change proposal states *"tuned-ppd provides a drop-in replacement for power-profiles-daemon"* and that *"power users can customize the desktop-exposed power profiles by editing /etc/tuned/ppd.conf"* (Fedora Project wiki, "TunedReplacesPower-profiles-daemon"; corroborated by Phoronix). Because `tuned-ppd` implements the PPD D-Bus API, GNOME's power slider now drives tuned. It sets the ACPI `platform_profile` and amd-pstate EPP. **This is the primary competitor for CPU power state on a modern Fedora install.** Detect with `tuned-adm active`; note the profile mapping in `/etc/tuned/ppd.conf`.
- **power-profiles-daemon:** Still available and may be present (older Fedora, or reinstalled). PPD "will then only control the platform_profile, while amd_pstate remains uncontrolled" in some configs. On Framework AMD, PPD has been Framework's recommended tool historically. Detect with `powerprofilesctl` / `powerprofilesctl version`.
- **Both PPD and tuned write the platform profile**, which on this SMU-driven platform effectively resets STAPM/PPT — meaning a profile switch will clobber your `ryzenadj` limits. The tool must either (a) pin the profile and reapply after any profile change, or (b) watch `/sys/firmware/acpi/platform_profile` and reassert.
- **TLP:** Not default on Fedora; if installed it conflicts with PPD/tuned and manages CPU scaling. It already ships a suspend/resume hook (`/usr/lib/systemd/system-sleep/tlp` calling `tlp suspend`/`tlp resume`) — a good template for your own reapply hook. Detect with `systemctl status tlp`.
- **GameMode (Feral):** On activation it changes the CPU governor (`desiredgov`, default `performance`), can set `platform_profile` (`desiredprof`), adjusts renice/ioprio, disables split-lock mitigation, and — **only if explicitly enabled** with `apply_gpu_optimisations=accept-responsibility` in `/etc/gamemode.ini` — sets NVIDIA `nv_powermizer_mode` and core/mem clock offsets (requires coolbits) or AMD performance level. By default it does **not** touch GPU clocks. Detect via `gamemoded -t`.
- **nvidia-powerd (NVIDIA Dynamic Boost daemon):** Manages Dynamic Boost — the dynamic CPU↔GPU power-budget sharing on NVIDIA laptops. It is what actually governs the RTX 5070's TGP within the platform budget (in lieu of `-pl`). It can receive an "SBIOS disable signal" and is entangled with AC/DC-detection bugs on some laptops. Detect with `systemctl status nvidia-powerd`. For a *minimize-noise* goal, leaving Dynamic Boost on is usually fine (it only *raises* GPU power opportunistically); the clock lock still caps the ceiling. But be aware it competes for the shared platform power budget.
- **AMD SmartShift:** SmartShift dynamically shares a single power pool between an AMD CPU and an **AMD** GPU. With an NVIDIA dGPU it does **not** apply. A Framework Community thread ("Framework 16 AMD SmartShift") indicates SmartShift Max is not even engaged on the FW16 with the AMD RX 7700S, let alone the NVIDIA module. **Conclusion: SmartShift is not a factor on the HX 370 + RTX 5070 configuration.** Platform power sharing is instead governed by (a) the AMD SMU/EC platform PPT for the CPU/iGPU side and (b) NVIDIA Dynamic Boost (`nvidia-powerd`) for the dGPU side, mediated by the Framework EC (`cpu_power.c` in the EC firmware).

### 5. Safety

**Consequences of too-low CPU limits.** Setting STAPM/PPT low is *generally safe*: RyzenAdj community guidance notes that lowering power/temperature limits is "usually relatively safe (you're simply reducing maximum performance)," in contrast to *raising* current/VRM limits (the `-g/-j/-k/-l/-m/-n` current limits), which is the genuinely dangerous direction. The realistic failure modes at extreme-low values are: sluggishness, workload stalls, and in rare cases instability/hangs if the SMU is starved — not permanent damage, and not a failure to boot (limits are not persisted to firmware, so a reboot clears them). There is no watchdog that bricks the machine for low PPT. Nonetheless, enforce a sane floor in the tool (e.g., do not set slow/STAPM below ~10–15 W) to avoid UI stalls and possible resume instability.

**Restoring defaults.**
- **CPU:** RyzenAdj has **no true "reset to firmware default"** command; the `--power-saving` / `--max-performance` flags map to CCLK-boost setpoint behavior (and read `nan` on this APU), not a full restore. The reliable ways to restore stock CPU limits are: (1) **reboot** (firmware/SMU reapplies defaults), or (2) have the tool record the stock STAPM/fast/slow values at first run and re-apply them. Switching the tuned/PPD profile also causes the platform to reassert its own limits.
- **GPU:** `nvidia-smi -rgc` (reset GPU/graphics clocks) and `nvidia-smi -rmc` (reset memory clocks) restore default clock behavior; NVML `nvmlDeviceResetGpuLockedClocks` does the same. These defaults also return on driver reload/reboot. Power limit needs no reset since it was never settable.

**Suspend/resume persistence.** This is the most important operational caveat:
- **CPU limits do NOT persist across suspend/resume.** The Framework AMD platform-profile-after-suspend bug means SMU limits are effectively reset/stale after resume until reasserted. Reapply `ryzenadj` on resume.
- **GPU clock locks likely do NOT survive suspend/resume** on mobile Blackwell. NVIDIA's docs state clock locks are lost on driver unload; RTX 50-series mobile has documented s2idle/RTD3 (D3cold↔D0) re-initialization and resume bugs (open-gpu-kernel-modules issues #1117, #905, #1064) during which the GPU reinitializes and would drop the lock. Persistence mode helps across driver reloads but is not guaranteed across a full RTD3 cycle. **Reapply the `-lgc` lock on resume too.**
- **Recommended mechanism:** a systemd sleep hook. Drop an executable script in `/usr/lib/systemd/system-sleep/` that reapplies both CPU (`ryzenadj`) and GPU (`nvidia-smi -lgc` / NVML) limits on the `post` argument (exactly as TLP does with its `pre`/`post` hook). Alternatively/additionally, a long-running daemon that subscribes to `org.freedesktop.login1` `PrepareForSleep` D-Bus signals and reapplies on wake — more robust than the sleep-hook directory (which systemd upstream calls "hacks," though they work in practice). A periodic watchdog (re-assert every N seconds) is a belt-and-suspenders defense against PPD/tuned/GameMode profile changes and post-resume resets.

## Recommendations

**Architecture (staged):**
1. **Phase 1 — Monitor only.** Read `fan1_input`/`fan2_input` (EC hwmon), `k10temp` Tctl, `amdgpu` PPT, NVIDIA temp/power/clocks (via `nvml-wrapper`), and CPU package power via `energy_uj` deltas. Empirically map `fan1`/`fan2` to physical fans and record max RPM by briefly forcing duty with `framework_tool`/`ectool`. **Confirm on-machine whether `nvidia-smi -lgc` succeeds and clamps clocks** (the one unverified assumption).
2. **Phase 2 — CPU shaping.** Use RyzenAdj ≥ v0.19.0 (with `ryzen_smu` ≥ 0.1.7, fallback `/dev/mem`) to set `--slow-limit`/`--stapm-limit` (and equal-or-higher `--fast-limit`), in mW, driven by a controller that targets a fan-RPM/noise ceiling. Enforce a floor (~10–15 W). Re-assert on a timer.
3. **Phase 3 — GPU shaping.** Enable persistence mode (`nvidia-smi -pm 1`), then lock the max graphics clock with NVML `nvmlDeviceSetGpuLockedClocks(dev, min, max)`, choosing `max` from the supported-clocks list (15 MHz granularity). Lower `max` until sustained GPU heat/fan RPM drop below target.
4. **Phase 4 — Coordination & persistence.** Detect and coordinate with `tuned`/`powerprofilesctl`, `nvidia-powerd`, GameMode, TLP. Install a systemd sleep hook **and** a `PrepareForSleep` D-Bus listener to reapply all limits on resume. Optionally pin the platform profile.

**Control policy.** Because the fans share one CPU+GPU cooling assembly, drive a single combined thermal/RPM target: when `max(fan1,fan2)` exceeds the user's RPM ceiling, step down whichever source (CPU PPT or GPU clock ceiling) is the larger heat contributor (use `energy_uj` CPU power vs. NVML GPU power to decide). Use hysteresis to avoid oscillation against the EC's own curve.

**Thresholds that change the plan:**
- If on-machine testing shows `nvidia-smi -lgc` is *also* rejected on this specific mobile GPU/driver, fall back to GPU-side control via `nvidia-powerd` behavior plus application-level frame/utilization caps (e.g., frame limiting), since no direct clock/power knob would remain.
- If RyzenAdj cannot set PPT on the installed BIOS/EC version, escalate to EC-firmware-level `cpu_power.c` limits (advanced, risky) or accept CPU-side control only via tuned/PPD profiles.
- If `energy_uj` is absent/zero on the running kernel, upgrade the kernel (needs the Family 1Ah RAPL support, upstreamed post-6.10) or use `zenpower5`.

## Caveats

- **Single biggest unverified assumption:** `nvidia-smi -lgc` clamping on the *mobile* RTX 5070 is *probable but not directly confirmed* — desktop Blackwell (RTX 5080) confirmations exist, but no mobile 50-series primary report was found. Test first.
- **Fan channel mapping, max RPM, and even fan count** for the FW16 depend on the installed module (the GPU module's page describes a single 75×11.5 mm fan, while the GPU-less module uses dual 75×8.2 mm fans); determine empirically. The claim that the fan(s) cool CPU and GPU together is grounded in Framework's own "cool the CPU and GPU simultaneously" description of the Graphics Module Fan, but the precise number/placement of tach channels with the RTX 5070 module installed should be verified.
- **EC fan-curve thresholds/hysteresis** are BIOS/EC-version-dependent and live in firmware source; the ~47 °C spin-up figure is a single community report on the 2024 AMD board and may differ on the 2025 HX 370 board/BIOS.
- **RyzenAdj on HX 370** is functional for PPT but PMTable readback is largely `nan`; behavior is version-dependent (use latest) and one report showed `ryzen_smu` init failure — validate on the installed kernel/module versions.
- **Version sensitivity throughout:** kernel (6.11+ for Zen 5 RAPL and amd-pstate heterogeneous-core handling), NVIDIA driver (610.x here; behavior has shifted repeatedly across 530/535/580/595), RyzenAdj/ryzen_smu, and Framework BIOS/EC. Re-test after any update.
- **Suspend/resume:** expect to reapply *all* limits after every resume; do not assume persistence, and log/verify reapplication given documented Blackwell-mobile RTD3/s2idle bugs and the Framework AMD platform-profile-after-suspend bug.
