# Rust Crate Stack for a Sudo TUI Thermal-Control Dashboard (2026 Edition)

## TL;DR
- **Build on a boring, synchronous "threads + channels" core:** ratatui 0.30.2 + crossterm for the UI, a dedicated 1 Hz sampler thread, a control-loop thread, and a ~30 fps render loop coordinated with `crossbeam-channel`; skip tokio/calloop unless you already need async elsewhere.
- **For hardware I/O prefer direct sysfs reads** (hwmon + `/sys/class/powercap/intel-rapl`) with a hand-rolled RAPL wraparound handler, use **nvml-wrapper 0.12.1** (actively maintained, NVML 12, loaded at runtime) for NVIDIA, and **shell out to `ryzenadj`** rather than depend on the stale `libryzenadj` 0.15.0 binding — with an NVML `set_gpu_locked_clocks` call preferred over `nvidia-smi -lgc`.
- **For control and plumbing, hand-roll the ~50-line PID and the RLS thermal model** (or use `pid` 2.0 / `linregress`), persist state with **serde + toml/serde_json**, log to a file via **tracing + tracing-appender**, and guarantee hardware reset via a combined **panic-hook + signal-hook + RAII `Drop` guard**. Under sudo, detect the real user via **`SUDO_USER`/`SUDO_UID`** because `directories`/`dirs` resolve paths to `/root`.

## Key Findings

### 1. TUI Framework
- **ratatui is the clear winner.** Current stable is **0.30.2** (the ratatui.rs installation page and homepage code sample both show `ratatui = "0.30.2"`; the 0.30 line went through alpha/beta releases across 2025–2026 before stabilizing). It is the actively maintained successor to the abandoned `tui-rs`, with ~21.2k GitHub stars, 4,500+ dependent crates, and 34.1M downloads. `cursive` remains a viable ncurses-style alternative but has a smaller ecosystem and a callback-driven architecture that fits a control-loop app less well.
- **As of 0.30, ratatui was split into `ratatui-core`, `ratatui-widgets`, and the umbrella `ratatui` crate.** Applications should depend on `ratatui`; only widget-library authors need `ratatui-core`.
- **Charting widgets:** For scrolling time-series, use the built-in **`Chart`** (line/scatter with `Dataset`, `Axis`, supports multiple datasets — ideal for temps/watts/RPM/clocks) and **`Sparkline`** (compact single-series bars; supports `RenderDirection::RightToLeft` for a scrolling feel and `Option<u64>` for absent values). For smoother/denser plots, the **`Canvas`** widget with braille markers gives sub-cell resolution. You maintain your own ring buffer (e.g., `VecDeque`) and window it each frame — Chart/Sparkline do not scroll themselves.
- **Event-loop pattern:** The recommended architecture is **plain threads + channels**: one input thread blocking on `crossterm::event::read`, one 1 Hz sampler thread, one control-loop thread (can be merged with sampler), and the main thread running a ~30 fps render tick. Communicate via `crossbeam-channel` (its `select!` + `tick` make combining a timer with event channels clean) or `std::sync::mpsc`. Prefer this over tokio unless async is otherwise needed; `calloop` is a callback/event-source model used by Wayland projects but is overkill here and blocks on dispatch.
- **Prior art worth studying:**
  - **bottom (`btm`)** — customizable graphical process/system monitor; a canonical example of live graphs (CPU/mem/network/temp) in ratatui. Uses a threaded collection model with an event enum sent over channels to the draw loop.
  - **bandwhich** — network utilization TUI; requires elevated privileges (documents the Linux capabilities-vs-sudo trade-off and the `sudo` `$PATH`/`env` pitfalls — directly relevant to your sudo concern).
  - **zenith** — in-terminal graphical metrics for *nix, including CPU/GPU (has NVIDIA support), a strong reference for GPU-stat TUIs.
  - **systemctl-tui** (rgwood) — a clean small ratatui app using the `tokio` + component/action architecture (based on the `ratatui` async template) if you do want an async reference.
  - **gping** — ping with a live line graph; minimal reference for a single scrolling Chart.

### 2. Sensors
- **hwmon:** Two options. **Direct sysfs reads** (`/sys/class/hwmon/hwmon*/temp*_input`, `fan*_input`, `pwm*`) are the "boring" choice — zero dependencies, trivial to parse (integers in milli-units), and give you full control. Alternatively, **`libmedium`** (current **0.13.4**, released ~9 months before mid-2026, actively maintained, Rust 2024 edition, **8,140,256 all-time downloads** across 36 published versions) is a pure-sysfs safe wrapper that models hwmons/temp/pwm sensors and, importantly, supports **writing** pwm values via its `writeable` feature — useful for fan actuation. The documented write path is exactly: `pwm.write_enable(PwmEnable::ManualControl).unwrap(); pwm.write_pwm(Pwm::try_from_percent(100.0).unwrap()).unwrap();` (via `hwmon.writeable_pwms()`). **`lm-sensors`** (bindings to `libsensors` via `sensors-sys`) is the other route but adds a C dependency and is more about read-only enumeration. **Recommendation: `libmedium` if you want typed sensors + pwm writes; direct sysfs if you want zero deps.**
- **RAPL watts from energy counters:** Read `/sys/class/powercap/intel-rapl:<zone>/energy_uj` (microjoules, `rw`) and `max_energy_range_uj` (the counter's wraparound modulus). Power = ΔE / Δt. Since the counter is a monotonically increasing accumulator that **wraps** (the underlying MSR has a wraparound time of ~60 s at high power draw on some domains), compute the delta with modular arithmetic:
  ```rust
  let mut delta = if cur >= prev { cur - prev } else { max_energy_range_uj - prev + cur };
  let watts = (delta as f64) / 1e6 / dt_secs;
  ```
  This handles the single-wrap case correctly. Note domain nesting: `intel-rapl:0` = package, `:0:0` = core, `:0:1` = uncore/dram, and `psys` (if present) = whole-platform. Don't sum nested domains (double counting). **AMD Ryzen (Fam17h/19h) RAPL support was added to the same `intel-rapl` powercap interface in Linux 5.11** (Linux 5.8 only added the separate `amd_energy` hwmon driver). **Reading `energy_uj` requires root** on modern kernels: after CVE-2020-8694 (the PLATYPUS side-channel), Linux 5.10 made powercap energy attributes root-readable only — fine here since you run under sudo.
- **NVIDIA (NVML):** **`nvml-wrapper` is actively maintained** — current **0.12.1 (released 2026-03-30)**, with 0.12.0 (2026-02-12) and 0.11.0 (2025-05-28) preceding it. It **currently targets NVML version 12**, and because NVIDIA guarantees NVML backwards-compatibility (per the crate README: *"Each new version of NVML is guaranteed to be backwards-compatible according to NVIDIA, so this wrapper should continue to work without issue regardless of NVML version bumps"*), it works across driver/NVML bumps — so **recent GPUs (RTX 50 "Blackwell") and recent driver branches are supported** as long as the installed `libnvidia-ml.so` is present. The wrapper **loads NVML at runtime via `libloading`** (not linked at build time), so a GPU-less machine just returns an init error you can gracefully handle. MSRV 1.60. Companion sys crate `nvml-wrapper-sys` 0.9.1. **Prefer `nvml-wrapper` over parsing `nvidia-smi`** output: it's faster (no process spawn), structured (typed values, no fragile text parsing), and gives you the same data source `nvidia-smi` itself uses.
- **AMD GPU equivalent:** No NVML analogue; read `amdgpu` via hwmon (`/sys/class/drm/card*/device/hwmon/`) or the `/sys/class/drm/.../device/gpu_busy_percent` and `pp_dpm_*` files. `rocm-smi` bindings exist but are immature; direct sysfs is the boring choice.

### 3. Actuation
- **ryzenadj:** A Rust binding exists — **`libryzenadj` 0.15.0** (safe bindings, LGPL-3.0, on gitlab.com/dragonn/libryzenadj-rs) over **`libryzenadj-sys`**, plus an alternative **`ryzenadj-rs`**. **However, `libryzenadj` is stale: still 0.15.0 and last released over a year ago** (its ~10k all-time downloads and 8 published versions reflect low adoption). Its `RyzenFamily` enum *does* include `Strixpoint` ("Zen 5 APU"), but it **lags the upstream FlyGoat/RyzenAdj C library**, which already defines newer families (Dragon Range, Krackan Point, Strix Halo, Fire Range) that the Rust binding is missing. **Recommendation: shell out to the `ryzenadj` binary** via `std::process::Command` for a single-binary app that must stay current with new silicon. It avoids linking LGPL code, avoids a stale FFI layer, and `ryzenadj` releases track new CPUs faster than the binding. The cost — a process spawn per adjustment — is negligible at 1 Hz. If you need to *read* SMU telemetry tightly, reconsider the binding, but for setpoint writes, subprocess is more robust. (Note: adjusting these values can destabilize or damage hardware — clamp aggressively.)
- **NVIDIA GPU clock locks:** **Prefer the NVML call** `Device::set_gpu_locked_clocks` (`nvmlDeviceSetGpuLockedClocks`) and `set_memory_locked_clocks`, with `reset_gpu_locked_clocks` to restore. This is superior to shelling out to `nvidia-smi --lock-gpu-clocks` / `-lgc` for the same reasons as above (no spawn, structured errors). Both ultimately require **root/admin**, which you have. Notes:
  - `set_gpu_locked_clocks` is supported on Volta+ (memory locked clocks Ampere+). The older `set_applications_clocks` path is deprecated (removed in CUDA 14) and unsupported on many consumer GeForce cards.
  - **Persistence mode** is only *required* for auto-boost changes; for locked clocks it's not strictly required but you'll get a warning if disabled. NVML persistence itself requires root.
  - "Locked" is a misnomer — the hardware thermal throttle still overrides your setpoint if the GPU overheats, which is exactly what you want as a safety backstop.
  - At 1 Hz actuation, latency of either approach is a non-issue; the NVML in-process call is just cleaner and more reliable.

### 4. PID / Control
- **PID crates (all mature, all tiny):**
  - **`pid`** — current **2.0.0**. The best-maintained: independent-form PID, per-term and total output limits, anti-windup via integral limit, derivative-on-measurement (no derivative kick), on-the-fly gain changes, generic float, `no_std`, optional serde. **This is the recommended crate if you use one.**
  - **`pid_lite` 1.2.0** — deliberately minimal `Controller::new(target, kp, ki, kd)`; nice `update_elapsed` for external dt. Last updated over a year ago but stable/complete (~26k downloads).
  - **`pid-ctrl` 0.1.4**, **`pid_control` 0.7.2** (old, ~10 yr, but battle-tested on 100+ kW motors and 346k downloads), **`pidgeon` 0.2.2**, **`advanced-pid` 0.2.3** — alternatives, less compelling.
- **Recommendation:** A thermal PID is ~50 lines. Given you need to combine it with a learned feed-forward model, log per-term contributions, handle variable dt (sampling jitter), and clamp to actuator ranges, **hand-rolling is defensible and gives full control** — but **`pid` 2.0.0** already implements every one of those niceties (per-term visibility, anti-windup, derivative-on-measurement, dt-agnostic), so use it unless you want zero deps.
- **Online/incremental regression (RLS) for the thermal model:**
  - **`linregress`** (OLS with statistics, R-style formula API) — batch, not incremental; fine if you refit over a sliding window.
  - **`smartcore`** — full ML library (linear/ridge regression on nalgebra/ndarray); heavyweight for a 2-variable model.
  - **`leastsquares`** — implements **Miller's updating regression** (`add_observation` one at a time, then `regress()`) — this is a genuine **online/recursive least-squares** primitive and the closest off-the-shelf match to "incrementally fit a thermal model" without loading the whole dataset in memory.
  - **`rust-recless`** (GitHub, SuperFluffy) — a dedicated recursive-least-squares implementation, though not a polished crates.io release.
  - **Recommendation:** For a **2-variable RLS with a forgetting factor**, **hand-roll it** (~30 lines with a 2×2 or 3×3 covariance update using `nalgebra` for the small matrix ops). Standard RLS with forgetting factor λ is well-specified, numerically simple at this size, and lets you tune adaptation rate — which no crate exposes cleanly. Use `leastsquares` only if you prefer a growing (non-forgetting) fit.

### 5. Plumbing
- **Config + state persistence:** **`serde` 1.0.228** (+ `derive` feature), **`toml` 0.8** for human-editable config, **`serde_json` 1.0.150** for the learned-model state file. All three are the canonical, battle-tested choices (serde has 1.1B+ downloads; serde_json 1.0B+). For the model state, JSON is a fine machine-written format; TOML is better for the user-facing config. Note the common gotcha: `toml` needs `serde` with `features = ["derive"]` explicitly. For atomic state writes, write to a temp file + `rename` to avoid corruption on crash/power-loss.
- **Logging that won't corrupt the TUI:** Use the **`tracing` + `tracing-subscriber` + `tracing-appender`** stack, **not** raw `println!`/`log`-to-stdout (which draws over the alternate screen and corrupts it — the ratatui forum explicitly notes "using a normal println will cause artifacts when rendering"). Route logs to a **file** so the TUI owns the terminal:
  ```rust
  let file_appender = tracing_appender::rolling::daily("/var/log/myapp", "app.log");
  let (nb, _guard) = tracing_appender::non_blocking(file_appender);
  tracing_subscriber::fmt().with_writer(nb).with_ansi(false).init();
  ```
  Keep the returned `WorkerGuard` alive for the program's lifetime (it flushes buffered logs on drop). Set `with_ansi(false)` for files. If you *also* want an in-TUI log pane, `tui-logger` (ratatui-only since v0.10) provides a `TuiTracingSubscriberLayer`. The `log` ecosystem works too but `tracing` is the modern default and composes layers (file + optional TUI widget) cleanly.
- **Graceful shutdown / guaranteed hardware reset — the critical safety requirement.** You must restore both (a) the terminal (raw mode off, leave alternate screen) and (b) hardware actuators (fan/clocks/power limits to safe defaults) on **normal exit, panic, AND SIGINT/SIGTERM**. Combine three mechanisms:
  1. **RAII `Drop` guard:** Wrap actuator reset in a struct whose `Drop` impl restores hardware defaults, and use ratatui's terminal restore for the screen. `Drop` runs on normal return and during unwinding panics. This is your primary path.
  2. **Panic hook:** Install a hook (before `ratatui::init`) that calls `ratatui::restore()` (disables raw mode, leaves alt screen) and then your hardware-reset routine, then chains the original hook. ratatui's `init` wraps the existing hook to restore the terminal first; supplement it with your hardware reset. Consider `color-eyre` for readable panic reports written to the log.
  3. **Signal handling:** `Drop` does **not** run on SIGINT/SIGTERM (the process is terminated), so install a handler. **`signal-hook`** is the recommended, widest-support crate: register `SIGINT`+`SIGTERM`, and in the handler set an `Arc<AtomicBool>` (or send on a channel) that your main loop checks, then break to run normal cleanup (Drop). Use **`ctrlc`** if you only need Ctrl-C (SIGINT). If you're on tokio, `tokio::signal` is the idiomatic equivalent. **Pattern:** signal handler flips a flag → main loop observes flag → returns → `Drop` guards fire (restoring terminal + hardware). For SIGKILL (uncatchable) you cannot clean up, so also reset defaults at *startup* as a belt-and-suspenders measure.

### Cross-cutting: Running TUIs under sudo
- **TERM / terminfo:** `sudo` often resets the environment; if it drops or the root environment lacks the terminfo entry for your `$TERM` (e.g., `xterm-ghostty`, `xterm-kitty`, or a newer `*-256color` variant not in root's ncurses DB), curses/terminfo-based tools fail with "unknown terminal type" or "missing or unsuitable terminal." crossterm (ratatui's default backend) does **not** use terminfo — it emits ANSI escapes directly — so ratatui is largely immune to this class of bug, a strong reason to prefer crossterm here. Still, to be safe: preserve `TERM` (and `TERMINFO`/`TERMINFO_DIRS`) across sudo (`sudo -E`, or `env "TERM=$TERM"`), or install the terminfo entry system-wide. Also mind sudo's `$PATH` stripping (`command -v` may fail) — as bandwhich documents, use `sudo env "PATH=$PATH" app` or full paths.
- **XDG / home-dir resolution:** When launched via `sudo`, `$HOME` becomes `/root` and `$XDG_CONFIG_HOME`/`$XDG_STATE_HOME` (if unset) resolve under `/root`. The **`directories` (6.0.0) and `dirs` (6.0.0, released 2025-01-12)** crates read these env vars/OS APIs directly, so `ProjectDirs`/`BaseDirs` will point at **`/root/.config`, `/root/.local/state`** under sudo — the wrong place if you want per-invoking-user config/state. (These crates deliberately don't special-case sudo; note their repos moved to Codeberg in 2025–2026.)
  - **Fix: detect the real invoking user via `SUDO_USER` / `SUDO_UID`.** If `SUDO_USER` is set, resolve that user's home (via the passwd database — e.g. `getpwnam` through the `nix`/`libc` crates, or the `users` crate — or read `/etc/passwd`) and build config/state paths under it, then `chown` any files you create to `SUDO_UID:SUDO_GID` so the user can edit them. Fall back to `directories`/`dirs` when `SUDO_USER` is unset (run as real root or a normal user). Be aware this workaround is brittle in nested cases (e.g., `sudo -iu foo` as another user) — validate that the resolved home is actually writable/accessible before using it.
  - For a **system daemon-style** tool that only ever runs as root, the cleaner choice is to skip XDG entirely and use fixed system paths: config in `/etc/myapp/`, state in `/var/lib/myapp/`, logs in `/var/log/myapp/`. This sidesteps the whole `SUDO_USER` dance and is the "boring" recommendation for a sudo-only hardware-control tool.

**Bottom line:** Use a synchronous, thread-based architecture with crossbeam channels; read sensors from sysfs directly (or via libmedium); use nvml-wrapper for both NVIDIA reads and clock locks; shell out to ryzenadj; use the `pid` crate but hand-roll the RLS; persist with serde/toml/json; log to file with tracing; and guarantee hardware reset with a layered Drop + panic-hook + signal-hook design. Because you run under sudo, prefer crossterm (no terminfo dependency) and either resolve `SUDO_USER` or use fixed system paths under `/etc` and `/var/lib`.

## Caveats
- **ratatui version** is 0.30.2 per the ratatui.rs installation page; confirm the exact patch level on crates.io before pinning, as the 0.30 line iterated through 2026.
- **libryzenadj**: the docs.rs "16 June 2026" timestamp is a docs-rebuild date, not a new release — the crate is still 0.15.0 and ~1+ year stale. Its GitLab last-commit date could not be independently confirmed; verify repo activity before depending on it.
- **RAPL wraparound** handling above assumes at most one wrap per sampling interval — true at 1 Hz for realistic power levels, but if you ever sample slower than the wrap period you can undercount; `max_energy_range_uj` is large (hundreds of GJ on modern parts) so wraps are rare on package domains but common on high-power sub-domains.
- **AMD RAPL** availability depends on kernel version: the unified `intel-rapl` powercap path for Ryzen landed in Linux 5.11; older kernels expose only the `amd_energy` hwmon driver (added in 5.8). Detect at runtime and fall back to hwmon.
- **NVML "locked" clocks** are still subordinate to the hardware thermal throttle — treat them as a ceiling/floor request, not a guarantee, and never rely on them as your only over-temp protection.
- **`dirs`/`directories` under sudo**: there is no *official* crate-doc statement prescribing the `SUDO_USER` fix; it's community/downstream knowledge (e.g., the `bob` project's issue tracker) plus a rust-lang libs-team note that `HOME` is unreliable under sudo/cron. Test your path resolution on your target distros.
- Some cached crates.io/docs.rs pages for older **nvml-wrapper** (0.9.0) still say "NVML version 11 / MSRV 1.51"; the current 0.12.x README (NVML 12, MSRV 1.60) supersedes them.
- Hardware actuation (ryzenadj SMU writes, RAPL power limits, GPU clock locks) can destabilize or damage hardware — clamp all setpoints to conservative ranges and always ship the startup-reset safety measure.
